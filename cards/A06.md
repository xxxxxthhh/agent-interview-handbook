# A06 · 长任务 goal Agent（口练卡）

> Design a long-running goal agent · 由 content/A06.md 生成，勿手改。

## 题面

> 某公司数据平台团队（虚构练习场景）要把 120 个遗留 ETL 作业从旧调度器迁到新调度器。负责人想给 Agent 一个目标：「把这 120 个作业迁完，每个都要对账通过」，然后让它自己跑几天，中间只在需要批准时找人。请在白板上设计这个长任务 Agent：它怎么知道自己做完了，中途崩溃、上下文被压缩、工具反复失败时怎么办。

题面为本书自拟的训练题，不代表任何公司的真实面试题或真实系统。

| 约束 | 取值（练习设定） |
| --- | --- |
| 量 | 120 个作业；每个作业要读旧配置 → 写新配置 → 在预发环境跑一次 → 对账（行数与关键列校验和） |
| 时长 | 预计 3–5 个工作日，跨多次会话；单次会话内上下文会被压缩多次 |
| 工具 | 旧调度器 API（只读）；新调度器 API（可写预发，生产切换需审批）；数据仓库查询（只读，每天 300 次配额）；代码仓库（可开 PR） |
| 不稳定 | 预发环境偶发失败，与作业本身无关；调度器 API 会限流 |
| 预算 | 总 token 预算、每天的仓库查询配额、5 个工作日的截止期 |
| 完成 | 每个作业要么「已切换且对账通过」，要么「移交给人并写明原因」 |
| 放行 | 生产切换由数据平台负责人逐个批准 |

**中途变化**：答到一半，面试官补一句——「负责人刚改了规则：对账除了行数和校验和，还要比较下游 3 张报表的数字；另外有 15 个作业要下线，不迁了。」

## 一句话框架

目标和验收条款放在会话之外、带版本号，由独立检查器判完成；进度记在账本里，恢复时先和真实环境对账；外层代码按作业切出短循环，预算、重试上限和升级给循环明确的停止条件。

## 追问（先口答，答不上的记进练习记录）

1. [为何不用备选] 为什么不让一个 Agent 在一个长会话里从头做到尾？反过来，为什么不直接写个脚本？
2. [需求变化] 对账规则加了「下游 3 张报表的数字」，另外 15 个作业下线。已经做完的怎么办？
3. [失败反证] Agent 报告「全部完成」，检查器也全绿，一周后下游报表的数字错了。问题出在哪？怎么防？
4. [恢复] 进程在「预发作业已经创建、还没来得及记账」时崩溃了，重启后怎么办？
5. [打转] 你怎么判断它在打转？预算用到 80% 还有 30 个作业没做完，怎么办？
6. [上下文] 压缩之后，模型按旧版规则做事，或者把一个已经移交的作业又捡了回来。怎么防？怎么测？
7. [评估] 你怎么评估这套 goal 机制本身，而不是某一次运行？
