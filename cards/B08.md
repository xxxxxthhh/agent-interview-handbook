# B08 · 错误恢复与幂等（口练卡）

> Retries, idempotency and recovery · 由 content/B08.md 生成，勿手改。

## 题面

> 你讲完一个会调用外部工具的 Agent，面试官接着问：「工具返回 429、调用超时、跑到一半进程被重新调度。你的 Agent 会不会把同一张工单开两次、同一封邮件发两次？重启之后它怎么知道自己做到哪一步了？」

题面为本书自拟的训练题，不代表任何公司的真实面试题或真实系统。

| 约束 | 取值（练习设定） |
| --- | --- |
| 任务 | 一个采购助理 Agent（虚构）：核对需求后在工单系统开采购单、更新内部 ERP 的预算占用、给供应商发确认邮件 |
| 工单系统 | 支持在请求里带幂等键，同一个键在保留期内重复提交只生效一次（保留期多长待核实）；限流时返回 429 并带 Retry-After |
| ERP | 不支持幂等键，但可以按业务单号查询是否已写入 |
| 邮件 | 发出去就收不回；发送接口只返回一个消息 ID |
| 运行环境 | Agent 跑在可被随时重新调度的 worker 上；有一个持久化的数据库可用 |
| 代价 | 重复开单、重复占预算要财务人工冲销；重复邮件会让供应商重复备货；漏发邮件只是延误 |

**中途变化**：答到一半，面试官补一句——「ERP 下个月升级成异步接口：提交只返回 202 和一个任务号，结果几分钟后才能查到。」

## 一句话框架

先把错误分类，再按动作的副作用选策略：读可以放心重试，写要有稳定的操作 ID、先查后重试、查不清就对账或交人；进度记在会话外的执行账本里，重启从账本恢复。

## 追问（先口答，答不上的记进练习记录）

1. [为何不用备选] 为什么不直接把错误信息给模型，让它自己决定要不要重试？
2. [需求变化] ERP 改成异步接口，提交只返回 202 和任务号，结果几分钟后才出来。怎么改？
3. [失败反证] 工单系统明明支持幂等键，线上还是出现了重复工单。可能是哪里出了问题？
4. [运行] 大促那天几十个 Agent 同时撞上工单系统的限流，重试把情况越弄越糟。怎么办？
5. [恢复] 进程在「开完采购单、还没更新 ERP」的时候被重新调度。新 worker 接手后怎么做？
6. [补偿] 采购单开了、预算也占了，最后发现供应商在黑名单上。怎么撤？
7. [评估] 你怎么证明这套恢复机制真的管用？
