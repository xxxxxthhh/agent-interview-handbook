# B02 · Tool / MCP 接口设计（口练卡）

> Tool and MCP interface design · 由 content/B02.md 生成，勿手改。

## 题面

> 你要把公司内部的订单、退款、工单系统接给客服 Agent。后端同事说：「我们已经有 40 个 REST 接口，自动生成一个 MCP server 全部暴露出去就行，模型自己会挑。」你怎么设计这层工具接口？怎么防止它选错工具、越权读别人的订单、重复退款？

题面为本书自拟的训练题，通常是在 A01 / A03 / A04 / A05 之后被追问出来的；它不代表任何公司的真实面试题或真实系统。

| 约束 | 取值（练习设定） |
| --- | --- |
| 现有接口 | 40 个 REST 接口，含查询、改地址、退款、建工单，也含几个运维用的管理接口 |
| 调用者 | 终端用户通过客服 Agent 使用；Agent 在服务端运行 |
| 副作用 | 退款、改地址、建工单都有副作用；退款接口超时后结果未知的情况时有发生 |
| 权限 | 用户只能看、只能操作自己名下的订单 |
| 模型 | 通用 LLM，会选错工具、会填错参数、会在出错后反复重试 |
| 协议 | 工具通过 MCP 暴露给 Agent；规范细节以 MCP 规范 2026-07-28 版为准 |

**中途变化**：答到一半，面试官补一句——「物流跟踪要接一家第三方公司提供的远程 MCP server，它的工具名、描述和 schema 都由对方维护，随时可能更新。」

## 一句话框架

工具是给模型用的产品接口，不是后端 API 的镜像：按任务收窄、读写分开、关键参数用 ID 和枚举约束；模型只提议，执行端按用户权限和业务规则校验，并用稳定的 operation_id 保证副作用只发生一次；工具的描述和返回内容也都是不可信输入。

## 追问（先口答，答不上的记进练习记录）

1. [为何不用备选] 为什么不把 40 个接口全暴露出去？模型够聪明，会自己挑。
2. [需求变化] 物流跟踪要接一家第三方的远程 MCP server，工具定义由对方维护。
3. [失败反证] 用户在对话里念了一个别人的订单号，模型照着调用了「查询订单」。
4. [副作用] 退款工具超时了，模型决定再调一次。
5. [错误设计] 模型收到一句「invalid request」，用同样的参数连续重试了 10 次。
6. [评估] 你怎么知道这套工具接口设计得好不好？
