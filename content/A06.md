## Prompt

> 某公司数据平台团队（虚构练习场景）要把 120 个遗留 ETL 作业从旧调度器迁到新调度器。负责人想给 Agent 一个目标：「把这 120 个作业迁完，每个都要对账通过」，然后让它自己跑几天，中间只在需要批准时找人。请在白板上设计这个长任务 Agent：它怎么知道自己做完了，中途崩溃、上下文被压缩、工具反复失败时怎么办。

题面为本书自拟的训练题，不代表任何公司的真实面试题或真实系统。

## Constraints

| 约束 | 取值（练习设定） |
| --- | --- |
| 量 | 120 个作业；每个作业要读旧配置 → 写新配置 → 在预发环境跑一次 → 对账（行数与关键列校验和） |
| 时长 | 预计 3–5 个工作日，跨多次会话；单次会话内上下文会被压缩多次 |
| 工具 | 旧调度器 API（只读）；新调度器 API（可写预发，生产切换需审批）；数据仓库查询（只读，每天 300 次配额）；代码仓库（可开 PR） |
| 不稳定 | 预发环境偶发失败，与作业本身无关；调度器 API 会限流 |
| 预算 | 总 token 预算、每天的仓库查询配额、5 个工作日的截止期 |
| 完成 | 每个作业要么「已切换且对账通过」，要么「移交给人并写明原因」 |
| 放行 | 生产切换由数据平台负责人逐个批准 |

**中途变化**：答到一半，面试官补一句——「负责人刚改了规则：对账除了行数和校验和，还要比较下游 3 张报表的数字；另外有 15 个作业要下线，不迁了。」

## Clarify

1. 每个作业的「完成」具体是什么、由谁判定？对账能否用脚本自动判？哪些只能人看？这决定检查器怎么建、完成由谁宣布。
2. 哪些动作有副作用、哪些必须人批准？预发能不能随便重跑？这决定幂等设计和放行点。
3. 预算有哪几种（token、墙钟、查询配额），用完时希望停下还是先交接？这决定硬上限和收尾方式。
4. 目标或验收规则中途会不会变、谁有权改？这决定目标要不要版本化、改条款要不要授权。
5. 任务会被打断吗（进程重启、会话结束、有人插手改了配置）？出问题时找谁？这决定恢复流程和升级路径。

## One-line frame

目标和验收条款放在会话之外、带版本号，由独立检查器判完成；进度记在账本里，恢复时先和真实环境对账；外层代码按作业切出短循环，预算、重试上限和升级给循环明确的停止条件。

## Decision table

| 设计点 | 采用 | 否决的备选 | 什么证据会让我改 |
| --- | --- | --- | --- |
| 目标与验收 | 目标文件带版本号，拆成逐作业的可检查条款（对账规则、状态要求；有依赖的作业还记录上游作业的配置版本）；Agent 只能读，改条款要负责人授权并升版本 | 目标只写在第一条消息里，靠模型记住 | 不改存放位置；条款粒度可以调，比如评测显示逐作业条款太碎、人工审核负担过重时，按作业类型合并 |

## Blank submission

在 25 分钟内交一版，至少覆盖：

- 数据流与控制流图：目标、账本、循环、检查器、人工审批各在哪；哪些状态活在会话之外。
- 「完成」由谁判定；Agent 自己说做完了，你凭什么信或不信。
- 一条恢复路径：进程在「已经创建了预发作业、还没来得及记账」时崩溃，重启后怎么办。
- 预算用完或在打转时怎么停，停下时交给人的是什么。
- 一个比 Agent 更简单的基线，以及从基线升级（或退回）的条件。

## Reference submission

![[fig:A06-flow|数据流与控制流。虚线框是会话之外的持久状态（目标文件、账本）；每个作业在独立的短循环里执行，检查器和预算检测都不经过模型；生产切换只在负责人批准之后发生。]]

**1. 目标是合约，不是一句话。** 负责人的目标先被拆成逐作业的验收条款：对账规则、状态要求、完成的定义，写进带版本号的目标文件。Agent 能读，不能改。目标含糊的地方先问一次再固定。条款改动要负责人授权，并把版本号加一。有上下游依赖的作业，条款里记下它所依赖的上游作业及其配置版本；上游重新切换或改了配置，下游的「通过」自动失效，要按新的血缘重验。

**2. 完成由检查器说了算。** 每个作业是否通过，由对账脚本判定，而不是由做事的模型宣布。报告里只列检查器的结果和证据（查询语句、对账数字），模型的自述只作参考。检查器、阈值和对账脚本放在 Agent 不能写的位置，否则它可以通过放宽检查来「完成」。

**3. 外层代码编排，每个作业一个短循环。** 编排器从账本取下一个待办作业，开一个独立上下文的循环：读旧配置、生成新配置、跑预发、对账、按失败原因修复。循环结束就回写账本、丢弃上下文。这样单个循环很短，压缩很少发生；作业之间也不会因为共享一个超长上下文而互相干扰。按 B01 的两条轴，这是「代码拆子任务」的编排。

**4. 账本是意图，环境是事实。** 账本记录每个作业的状态、尝试过什么、下一步。重启或换会话时，不从聊天记录推断进度，而是先查调度器和预发的真实状态，与账本逐个对账；两者不一致时以真实状态为准并补记。

**5. 副作用只在能确认时才自动重试。** 创建预发作业、开 PR 都带稳定的 operation_id（作业 ID + 动作种类 + 目标环境 + 配置哈希），避免不同动作共用一个标识。只有下游对这个 ID 有经过验证的唯一约束或幂等窗口时，才自动用同一个 ID 重试。否则先按 ID 查询；查不到也不能断定没写入，因为外部可能已经写入、只是本地没记账或暂时查不到。这时不自动重发，把作业标成「待核对」，稍后再查或交给人。本地账本记了 ID，并不保证外部只有一份。生产切换 Agent 只能提交申请；负责人批准后由确定性脚本执行。Agent 使用的服务身份只读旧调度器、只写预发，只能查询这 120 个作业涉及的表。

**6. 预算、打转与升级。** 三种预算各有硬上限。打转的信号：同一作业的同一检查连续失败、同一个修改被反复提交、若干轮内通过检查器的作业数不变、成本在涨而进展为零。检测到打转先换一次策略（比如换一种修复思路），仍不行就把该作业移交给人。任一预算用到 80% 时，先写交接包再停：哪些已完成（附检查器证据）、哪些移交（附原因和尝试记录）、哪些没开始。

**7. 上下文与缓存。** 目标和条款是钉住区块，压缩时原样重新注入，不参与摘要。进度靠工具读账本，不写进 system prompt。prompt 按稳定程度排序：system、工具定义、钉住区块在前且字节级不变，观察只往后追加。压缩会改写摘要及其后的内容，这一段的缓存要重新写入；稳定前缀只要字节不变、仍在缓存有效期内，按服务的前缀匹配规则仍可命中。所以压缩只在循环边界发生，也不去改动前缀。

**8. 评估这套机制。** 在沙箱里复制一批历史作业做固定任务集，量真实完成率、假完成率（自称完成但检查器或人工不通过）、单作业成本、升级率、恢复成功率、压缩后的目标漂移率。改机制前后在同一任务集上对比，口径与 B06 一致。

**基线与升级条件。** 最简单的基线是「确定性转换脚本 + 人工处理异常」：能机械转换的配置用脚本批量转，对账脚本判通过，转不了的交给人。只有脚本覆盖不了的配置变体多到人工处理不过来时，才让模型处理这部分作业；如果模型处理的作业假完成率或返工率高于人工，就退回脚本 + 人工，让模型只给修改建议。

## Rubric

| 维度 | 及格 | 优秀 | 常见失分 |
| --- | --- | --- | --- |
| 问题定义 | 问清完成标准和放行点 | 问到预算种类、条款谁能改、中断的形态，并由此推出版本化与恢复设计 | 直接开始讲 Agent 循环 |
| 架构取舍 | 目标和进度存在会话外 | 外层代码按作业切短循环，讲清为什么不用一个超长会话，给出依赖作业的处理 | 一个会话跑到底，靠压缩撑着 |
| 失败与恢复 | 提到重试和人工兜底 | 崩溃时账本与环境对账、operation_id、打转检测和交接包都讲到 | 只说「失败就重试」 |
| 评估 | 提到检查器 | 区分真实完成与假完成，给出机制本身的评测指标，检查器不在 Agent 可写范围 | 相信 Agent 的完成报告 |
| 表达 | 2 分钟内讲完主干 | 先给「目标是合约」的结论，再展开；追问时能说出具体阈值和触发条件 | 罗列组件，没有取舍 |

## Two-minute English

I'd treat the goal as a contract that something outside the model verifies. First I'd ask what "done" means for each job, which actions need approval, and what budgets we have.

The goal becomes versioned acceptance criteria per job, stored outside the conversation. The agent can read them but not change them; changes need the owner's approval and a new version.

Done is decided by a checker, not by the agent. Here, a reconciliation script compares row counts and checksums.

The outer loop is plain code. It picks the next job from a ledger and runs a short, isolated agent loop for that job, then writes the result back. Short loops mean little compaction.

The ledger records intent; the environment is the truth. On restart, I reconcile the ledger with the scheduler before doing anything. Every write carries a stable operation ID, but I retry automatically only where the scheduler verifiably deduplicates it; otherwise an unclear result stops that job for review.

Budgets are hard limits. If the same check keeps failing or no new job passes for several turns, the agent tries one different approach, then hands the job to a person. At eighty percent of budget, it writes a handoff instead of getting cut off.

Finally, the goal block is pinned during compaction, and the prompt is ordered by stability so the prefix stays cacheable.

## Follow-ups

### [为何不用备选] 为什么不让一个 Agent 在一个长会话里从头做到尾？反过来，为什么不直接写个脚本？

- 一个长会话里，120 个作业的观察不断堆积，压缩会反复发生，每次压缩都是一次丢细节、丢目标的机会，摘要及其后的缓存片段也要重新写入；估算里单一长会话的输入量约是按作业切分的 3.5 倍。
- 按作业切分后，每个循环只看一个作业的上下文，失败也只影响这一个作业；代价是作业之间的依赖要显式传递。
- 能用脚本转的就用脚本，这是基线。只有脚本覆盖不了的配置变体多到人工处理不过来，模型才值得进来；判断依据是同一任务集上的假完成率、返工率和人工工时。

### [需求变化] 对账规则加了「下游 3 张报表的数字」，另外 15 个作业下线。已经做完的怎么办？

- 目标文件升到 v2，条款变更由负责人授权。账本里每个作业记下它是按哪个版本判定通过的。
- 已「对账通过」但还没切换的作业，按 v2 只补做新增的报表比较，不必重迁；已切换到生产的作业也按 v2 重验，不通过的交负责人决定是否回滚，Agent 不自行回滚生产。
- 15 个下线作业改为「已取消」并写明原因，不删除历史记录；它们已经创建的预发资源按清单交给人清理。
- 重算配额和工期，按变更那一刻的实际进度算：已对账且保留的作业只补新增的 3 次查询，没做的按 9 次，取消作业已经花掉的查询是沉没成本；再加上失败重跑，按每天剩余配额排期（见估算）。从零按 v2 算的 945 次、4 天只是下限情景。
- 工期还要算负责人逐个批准的时间。算下来不够就提前告诉负责人，请他决定加配额、延期还是缩小范围。

### [失败反证] Agent 报告「全部完成」，检查器也全绿，一周后下游报表的数字错了。问题出在哪？怎么防？

- 检查器全绿只说明「条款里写到的都满足」；报表错说明验收条款没覆盖到下游，这是条款的缺口，不是执行的问题。
- 另一种可能是 Agent 动了检查器：改了对账阈值、跳过了某些列。所以检查器、阈值和对账脚本必须放在 Agent 不能写的地方，报告里附上检查器的版本和原始输出。
- 还有一种形态：上游作业切换后输出变了，下游作业却是按旧的上游版本验证通过的。所以有依赖的作业，条款要记上游的配置版本；上游一变，下游的「通过」自动失效并重验。两个作业都按同一血缘版本通过，才能一起宣布完成。
- 防：高风险作业（下游报表多的）加人工抽检；条款里加入下游比较。发现后：条款升版本，按新条款重验所有已完成的作业，回溯受影响的范围，并把这个样本加进评测集。

### [恢复] 进程在「预发作业已经创建、还没来得及记账」时崩溃了，重启后怎么办？

- 重启先对账：按账本里「进行中」的作业，用 operation_id 查调度器，看预发作业是否存在、状态如何。
- 查到了就补记账本，从下一步继续。
- 没查到时分两种情况：下游对这个 ID 有经过验证的唯一约束或幂等窗口，才用同一个 operation_id 重试；没有的话不自动重发，因为外部可能已经写入、只是暂时查不到，把作业标「待核对」，稍后再查或交给人。
- 查询本身失败或结果矛盾时也不猜，同样标「待核对」，其余作业继续。

### [打转] 你怎么判断它在打转？预算用到 80% 还有 30 个作业没做完，怎么办？

- 打转的可观察信号：同一作业同一检查连续失败；同一个配置差异被反复提交；若干轮内通过检查器的作业数不变；token 在涨而进展为零。
- 阈值要按实测的随机失败率定：预发随机失败率 10%、失败彼此独立时，最多尝试 3 次（首次 + 2 次重试），无辜作业被误升级的概率约千分之一；最多尝试 2 次则约百分之一（见估算）。
- 用到 80% 时先写交接包：已完成的附检查器证据，未完成的按「在做 / 没开始 / 已移交」分组，写明卡在哪、试过什么。然后请负责人决定是追加预算、缩小范围还是转人工。

### [上下文] 压缩之后，模型按旧版规则做事，或者把一个已经移交的作业又捡了回来。怎么防？怎么测？

- 防：目标和条款是钉住区块，压缩时原样注入，带版本号；作业状态以账本为准，每个循环开始时从账本读，而不是从摘要里推断。
- 缓存：钉住区块放在前缀里且字节级不变；版本升级时，从目标块开始往后的缓存要重新写入一次，这是有意的。
- 测：在评测里人为触发压缩，让模型复述当前目标版本、当前作业和下一步，与账本比对；统计压缩后的目标漂移率和「捡回已移交作业」的次数。

### [评估] 你怎么评估这套 goal 机制本身，而不是某一次运行？

- 在沙箱里复制一批历史作业做固定任务集，注入已知故障（预发随机失败、API 限流、中途崩溃、中途改条款）。
- 指标：真实完成率、假完成率、单作业成本、升级率、恢复成功率、压缩后漂移率；机制改动前后在同一任务集上配对比较。
- 同一任务重复跑多次看一致性，口径按 B06 的 pass^k：长任务更关心「每次都能完成」，而不是「试几次总有一次成功」。

## Failure cards

### 假完成

- **症状**：Agent 的完成报告说「全部完成」，但检查器没跑、跑失败了，或者人工抽检不通过。
- **根因**：让做事的模型自己宣布完成；检查器的结果没有进入报告，或者检查器在 Agent 可写的范围里。
- **防线**：完成只由检查器判定，报告只列检查器的输出和版本；检查器、阈值放在 Agent 不能写的位置；评测里单独统计假完成率。

### 账本和现实分叉

- **症状**：同一个作业在预发里出现两份，或者账本说已完成、调度器里却找不到。
- **根因**：崩溃发生在「副作用已发生」和「账本已记录」之间；重启后按账本继续，没有先对账。
- **防线**：所有写操作带稳定的 operation_id；只有下游验证过按 ID 去重，才自动重试；重启先按 ID 查询真实状态再继续；查不清的作业标「待核对」交给人，不自动重发。

### 压缩后目标漂移

- **症状**：规则改成 v2 之后，模型仍按 v1 判；或者重复做已完成的作业、把已移交的作业捡回来。
- **根因**：目标和进度只存在对话里，被摘要改写或丢失。
- **防线**：目标钉住并带版本号，进度以账本为准；按作业切短循环让压缩少发生；压缩后的复述回归测试。

## Estimate

**问：按作业切短循环和一个长会话，token 差多少？尝试上限设几次？新规则下配额够不够？**

假设（练习设定，全部待实测）：120 个作业；每个作业平均 12 轮模型调用；每轮输入 = 稳定前缀 8k tokens（system、工具定义、钉住的目标块）+ 作业上下文平均 10k tokens，输出 1k tokens；短循环里前缀缓存命中率 90%。单一长会话：每轮新增约 2.5k tokens 历史，上下文涨到 100k 就压缩回 20k，平均上下文约 60k；每次压缩额外一次调用，读入 100k。预发随机失败率 10%，与作业本身无关、各次独立；「尝试上限」指总尝试次数，含首次。每个作业对账需 6 次仓库查询，新规则下需 9 次。中途变化在第 3 个工作日开始时到达：此时 40 个作业已按旧规则对账通过并保留，另有 5 个已对账的作业被取消，10 个还没做就被取消、没有消耗查询，其余 65 个还没做（40 + 5 + 10 + 65 = 120）；约 15% 的作业需要重跑一次对账。负责人批准一个切换约 3 分钟。

```
token（方案 X：按作业切短循环）
  轮数        120 作业 × 12 轮                   = 1,440 轮
  输入        1,440 × (8k + 10k)                 = 25.92M tokens
  输出        1,440 × 1k                          = 1.44M tokens
  其中可缓存前缀  1,440 × 8k × 90%                = 10.368M tokens
  未命中缓存部分  25.92M − 10.368M                = 15.552M tokens

token（方案 Y：单一长会话 + 压缩）
  每个压缩周期    (100k − 20k) / 2.5k            = 32 轮
  压缩次数        1,440 / 32                      = 45 次
  输入        1,440 × 60k + 45 × 100k             = 86.4M + 4.5M = 90.9M tokens
  Y / X 输入比                                    ≈ 3.5 倍

尝试上限（一个作业本身没问题，却因随机失败被误升级；失败独立时的期望值）
  最多 3 次    0.1³ = 0.001  × 120 作业           ≈ 0.12 个
  最多 2 次    0.1² = 0.01   × 120 作业           = 1.2 个

仓库查询配额（每天 300 次）
  原规则，从零开始  120 × 6                        = 720 次 → 至少 3 天
  v2 从零开始（下限情景） (120 − 15) × 9          = 945 次 → 至少 4 天
  中途变更（第 3 天开始时）
    已通过并保留，补查  40 × 3                      = 120 次
    未做，按 v2         65 × 9                      = 585 次
    取消作业已花掉的    5 × 6 = 30 次（沉没，不占剩余配额）
    未做即取消          10 × 0 = 0 次
    重跑 15%            65 × 15% × 9 + 40 × 15% × 3  = 87.75 + 18 ≈ 106 次
    合计                                            ≈ 811 次
    剩余配额：第 3–5 天整天可用 3 × 300              = 900 次 → 余约 89 次
    若第 3 天只剩 120 次 120 + 2 × 300               = 720 次 → 缺约 91 次

负责人批准     105 个作业 × 3 分钟                    = 315 分钟 ≈ 5.3 小时
```

**结论**：按作业切短循环的输入量约为单一长会话的 1/3.5；长会话的 45 次压缩，意味着摘要及其后的缓存片段 45 次重新写入或未命中，也是 45 次丢细节的机会。最多尝试 3 次时误升级几乎可以忽略，2 次则每轮约误升级 1 个作业。中途变化之后，真正卡工期的是查询配额：按变更时的进度算约 811 次，第 3–5 天整天可用时只余约 89 次；变更如果在第 3 天下午才到、当天只剩 120 次，就缺约 91 次，要提前请负责人决定。另外负责人还要花约 5.3 小时逐个批准切换，这也要排进他的日程。

**敏感性**：预发随机失败率从 10% 升到 30%，最多尝试 3 次的误升级变为 0.027 × 120 ≈ 3.2 个，2 次变为 0.09 × 120 = 10.8 个，这时该先修预发环境，而不是一味提高上限。如果失败彼此相关（例如预发整体故障一小时），120 × p³ 只是独立情景下的期望值，实际会成批出现，要按时间窗口看失败是否扎堆。每个作业的轮数从 12 升到 20，方案 X 的输入变为 120 × 20 × 18k = 43.2M。方案 Y 如果只追加不改写，增长的历史也能部分命中缓存，与 X 的实际费用差距会小于 3.5 倍；但每次压缩后，摘要及其后的片段仍要重新写入缓存，细节丢失也仍在。

**没算的**：预发环境本身的计算费用、「待核对」和移交作业的人工处理时间、失败作业的 token 重试成本。

**怎么实测**：先在沙箱里跑 10 个作业，记录每个作业的实际轮数、每轮输入输出 token、缓存命中率、预发失败的次数与原因、每个作业的查询次数；用实测值替换上面每个假设，再按每天剩余配额重排工期。
