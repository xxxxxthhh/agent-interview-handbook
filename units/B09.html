Latency and cost under SLA延迟与成本

口述 2 min 追问 7 层 适合 垂直 Agent 研发, FDE, Solutions
Prompt 题面

先想清楚再开口

你讲完一个会调工具的 Agent，面试官接着问：「现在 p95 要 8 秒内出完整答案，下个季度预算还要砍掉 40%。你先动哪里？怎么证明质量没掉？」

题面为本书自拟的训练题，不代表任何公司的真实面试题或真实系统。场景为虚构练习设定。

约束

约束取值（练习设定）
系统企业内部运营助手：每个请求先由模型规划，再调 2–4 个内部工具（查工单、查库存、查政策），最后由模型汇总作答
量每天约 20,000 个请求，按 30 天计每月约 600,000 个
SLA从提交到完整答案 p95 ≤ 8 秒；首字 p95 ≤ 2 秒
质量门槛在现有分层评测集上，正确率与规则违反率都不能比现状差
安全权限校验、输出校验不参与降级
成本下季度模型费用预算比本季度少 40%
数据已有每个请求的整轮 trace：各段耗时、每次调用的输入输出 token
答到一半再点开：面试官补了一句

「市场部要在月底做一次推广，那三天请求量是平时的 4 倍，预算不追加。」

该先问的问题

  1. SLA 量的是哪个时点——首字、首个有用内容，还是完整答案？按什么分层（意图、租户、是否峰值）？这决定优化目标和怎么验收。
  2. 质量门槛用哪套评测集、哪些指标？所有降本、提速方案都要过同一道门，否则省下的钱是拿质量换的。
  3. 预算限的是每请求、每租户还是每月总额？超了以后允许降级到什么程度，哪些东西绝不降级？
  4. 现在的 trace 里，时间和 token 各花在哪一步？整轮 p95 慢的请求有什么共同点？没有这张账，任何优化都是猜。
  5. 请求分布怎样：简单意图占多少？每次调用里不变的前缀（system prompt、工具定义）有多长？这决定路由和缓存能省多少。

一句话框架

先用整轮 trace 找出关键路径和钱花在哪一步，再在质量与安全门槛不动的前提下，比较「少走一步」和「每步更快」各能省多少；流式只改善体感，不缩短完成时间。

设计取舍表

设计点采用否决的备选什么证据会让我改

流式输出最终答案流式输出，改善首字；工具结果没回来之前，只给如实的进度提示用流式掩盖慢的完成时间；把未校验的动作结论先流给用户用户侧数据显示首字改善后放弃率没降，说明体感瓶颈在完成时间，回到关键路径上优化
成本上限与降级每请求设模型调用次数和 token 上限，月度预算按日告警；超限时按事先定好的顺序降级：压缩上下文 → 小模型 → 只返回检索结果并提示转人工。每一层降级都要按意图预先过质量门槛，哪类意图在哪一层不达标，就对它直接排队、限流或转人工，而不是降级。权限与输出校验不降级超预算直接截断输出；或关掉校验步骤来省钱降级后质量回归超出门槛，改为排队或限流，而不是继续降级

展开 2 分钟英文口述稿

I'd start from the trace, not from the model price. For each request I want one end-to-end trace, so I can see the critical path and where the tokens go. Adding up per-step p95s doesn't give you the end-to-end p95, so I measure the whole request, split by intent and tenant, and track first token and full answer separately.

Then I compare two kinds of wins: fewer steps and faster steps. Fewer steps usually wins — plan independent tool calls in one pass, run them in parallel, and move deterministic work out of the model loop. Faster steps means routing simple intents to a smaller model, with escalation rules and its own evaluation.

For cost, the biggest lever is often the stable prefix. Keep the system prompt and tool definitions byte-identical at the front so they can be cached, and append everything that changes. I treat the hit rate and cache pricing as parameters and fill them from real usage data.

Streaming helps perceived latency, not completion time, and it should never stream an unverified action.

Every change has to pass the same layered eval. And there's a written degradation order for budget overruns — shorter context, smaller model, then retrieval only — but permission and output checks never degrade.

Follow-ups 追问

一层一层往下问

  1. 为何不用备选为什么不直接全换成更便宜、更快的小模型？
    先口答，再展开要点
    • 单价降了，但质量可能静默回归：简单意图没问题，复杂意图出错，总的正确率被平均掉了，要看分层评测。
    • 路由是折中：小模型处理可分类的简单意图，按规则或置信度升级；误路由要算两种代价——简单题被送去大模型是浪费钱，复杂题被留在小模型是质量事故。
    • 触发改变的证据：分层评测里，某类意图走小模型后仍在门槛之上，才把它划给小模型。
  2. 需求变化预算砍 40%，SLA 不变，你按什么顺序动手？
    先口答，再展开要点
    • 先算账：用 trace 看 token 花在哪一类调用、哪一段前缀、哪一类意图。钱花在哪里，就先动哪里。
    • 按「风险低、收益可测」排序：稳定前缀以提高缓存命中 → 合并规划减少往返 → 裁剪工具返回的冗余字段 → 路由简单意图。每一步都单独过评测门槛，并记录它实际省了多少。
    • 最后才是降级策略，而且要说清降级后的质量是多少，由业务方签认，不在上线后才发现。
    • 月底推广的 4 倍流量，要先确认是总额预算还是单价预算。总额不变时，把推广期的量并进当月总量，和砍 40% 后的月上限相减（见估算）：只靠缓存几乎没有余量，缓存命中率掉下来还会超线，所以合并规划要在推广前上线，并事先定好超线时哪些意图排队或限流，而不是临时降质。
  3. 失败反证上线并行工具调用后，p50 降了，p95 反而升了。为什么？
    先口答，再展开要点
    • 并行后整轮要等最慢的那个分支：分支越多，碰到某一个分支慢的概率越高，尾延迟被放大。
    • 并发请求可能触发下游限流，429 之后的重试又把尾延迟推高。
    • 处理：给每个分支设超时，超时就带着部分结果作答并说明缺什么；限制并发度；只对幂等的只读查询做对冲请求（hedged request）；按分支统计尾延迟，找出真正拖后腿的那个。
  4. 流式首字已经很快了，用户还是说慢。
    先口答，再展开要点
    • 流式只改善首字，不缩短完成时间；如果答案依赖工具结果，工具回来之前能流出的只是进度提示。
    • 要量「首个有用内容」的时间：带上查询结果或结论的那一刻，而不只是第一个字。
    • 进度提示要如实（「正在查询工单系统」），不能先流出一个还没被工具结果证实的结论。
  5. 缓存缓存命中率只有 20%，为什么？怎么查？
    先口答，再展开要点
    • 最常见的原因是前缀不稳定：system prompt 里有时间戳、用户名或每次不同的检索结果；工具定义的顺序每次不同；多个版本的 prompt 同时在线。
    • 另一类原因是请求太稀疏：同一前缀的两次请求间隔超过缓存有效期（具体时长看所用平台，当参数处理）。
    • 查法：从调用返回的用量字段统计缓存读取与写入的 token，按 prompt 版本和租户分组；找出前缀里第一个变化的位置，把变化的内容挪到后面。
  6. 成本上限某个请求烧掉了平均值 50 倍的 token。
    先口答，再展开要点
    • 常见原因：模型在工具之间打转，或者某个工具返回了巨大的结果被整段塞回上下文。
    • 每请求设模型调用次数和 token 上限；工具结果分页或裁剪，只返回需要的字段。
    • 触顶时停下，返回已有的部分结果并说明原因，同时告警；按租户统计异常请求的比例。
    • 省钱不能关掉权限或输出校验：这些检查是安全门槛，不在降级顺序里。
  7. 评估路由器本身怎么评估？
    先口答，再展开要点
    • 在带意图标签的请求集上看路由的混淆矩阵：哪些复杂请求被送去了小模型，哪些简单请求被送去了大模型。
    • 按路线分别报告质量：小模型那一路的正确率要单独过门槛，不能被大模型那一路的高分平均掉。
    • 新的路由规则先在影子模式下跑：只记录「会被送到哪里」，不改变实际路由，和现行版本对比后再切换。
Failure Modes 失败模式

这些地方最容易栽

把分段 p95 相加当成整轮 p95
  • 症状：设计评审时各段预算加起来刚好卡在 SLA 以内，上线后整轮 p95 却超标；或者反过来，预算看着超了，实际大多数请求没事。
  • 根因：各段的慢请求未必落在同一个请求上，p95 不能相加；而并行分支会让整轮等最慢的那个，尾部被放大。
  • 防线：用同一请求的整轮 trace 统计 p50 / p95，并按意图和是否峰值分层；分段预算只用来找关键路径，不用来宣布达标。
降本后质量静默回归
  • 症状：成本降下来了，整体正确率只掉了一点点，几周后某类复杂请求的投诉集中出现。
  • 根因：只看了总体指标；小模型或裁剪上下文对复杂意图的影响被简单意图的高分平均掉了。
  • 防线：每个降本改动都过分层评测，按意图报告；路由按路线分别过门槛；上线后按意图盯人工推翻率和投诉。
并行放大尾延迟
  • 症状：p50 明显下降，p95 和 p99 反而上升；下游服务开始出现限流错误。
  • 根因：整轮等最慢的分支；并发打到下游触发限流，重试让尾部更长。
  • 防线：分支超时并带部分结果作答；限制并发度；只对幂等的只读查询做对冲请求；按分支统计尾延迟。
Estimate 估算

带着量纲算一遍

问：预算砍 40%，靠缓存、合并规划和路由分别能省多少？请求量涨到 4 倍呢？

假设（练习设定，全部待实测）：每月 600,000 个请求；现状每个请求 3 次大模型调用（规划、看完工具结果再想一次、汇总）；每次调用输入 = 6k tokens 稳定前缀 + 2k tokens 变化内容，输出约 400 tokens。缓存命中率 c = 0.8，缓存读取的计价是正常输入的 r = 0.1 倍。60% 的请求是简单意图，可走小模型，小模型单价是大模型的 s = 0.2 倍；其中 10% 被小模型处理后仍需升级到大模型（两边都付费）。只比较输入 token，折算成「大模型等价 token」。

每请求输入（大模型等价）
  现状       3 次 × (6k + 2k)                        = 24.0k
  + 缓存     前缀折算 6k × (0.8 × 0.1 + 0.2) = 1.68k
             3 次 × (1.68k + 2k)                     = 11.04k   （−54%）
  + 合并规划 2 次 × 3.68k                            = 7.36k    （−69%）
  + 路由     7.36k × (60% × 0.2 + 60% × 10% + 40%)
           = 7.36k × 0.58                            = 4.27k    （−82%）

每月输入（大模型等价）
  现状       600,000 × 24.0k  = 14.4B
  缓存+合并  600,000 × 7.36k  = 4.42B

推广期 3 天 × 4 倍流量（每天 20,000 → 80,000）
  多出来的请求   3 × 60,000               = 180,000 个
  当月请求总量   600,000 + 180,000         = 780,000 个

当月上限：砍 40% 后   14.4B × 60%          = 8.64B
  缓存+合并        780,000 × 7.36k   = 5.74B   余量 2.90B
  只用缓存         780,000 × 11.04k  = 8.61B   余量 0.03B
  命中率 30%+合并  780,000 × 12.76k  = 9.95B   超出 1.31B

怎么读：在这组假设下，平常月份只靠缓存就能把每请求输入降 54%，超过要求的 40%；但推广期要把量并进当月总量再和上限相减。含推广的当月，只靠缓存只剩 0.03B 的余量，几乎贴线；加上合并规划还有 2.90B 余量；如果推广期缓存命中率掉到 30%，即使合并规划也会超出 1.31B，要事先定好超线时哪些意图排队或限流。路由是再往下的余量，必须先过质量门槛才算数。这只是输入侧的筛选：输出 token（现状每请求约 1.2k，合并规划后约 0.8k）、缓存写入、工具与检索服务、基础设施的成本都没算；要证明模型费用预算达标，得用全口径公式：月费用 = （总输入 − 缓存读取 − 缓存写入）× 普通输入单价 + 缓存读取 × 读取单价 + 缓存写入 × 写入单价 + 输出 × 输出单价，三类输入互斥计数；若所用服务把写入价定义为附加费，就只加它相对普通输入价的差额。再加工具与基础设施费用，用实测值代入。

敏感性：命中率只有 c = 0.3 时，前缀折算为 6k × (0.3 × 0.1 + 0.7) = 4.38k，只靠缓存是 3 × 6.38k = 19.14k（−20%），不够；加上合并规划是 2 × 6.38k = 12.76k（−47%），刚好过线。小模型单价比 s = 0.5 时，路由后为 7.36k × (0.3 + 0.06 + 0.4) = 5.59k，路由的收益明显缩小。结论对 c 和 s 都很敏感，先测它们再定方案；尤其要测推广期流量上来后的命中率，而不是只测平常月份。

怎么实测：从调用返回的用量字段统计每次调用的输入、缓存读取、缓存写入和输出 token；按 prompt 版本和意图分组算实际命中率；在评测集上跑合并规划和路由的版本，记录质量与每请求 token；向财务确认 r、s 和大模型单价，用实测值替换上面每个假设，再重算。
