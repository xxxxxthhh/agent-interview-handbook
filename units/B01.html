Workflow, agent, or multi-agent?编排光谱

口述 2 min 追问 6 层 适合 FDE, Solutions, 垂直 Agent 研发
Prompt 题面

先想清楚再开口

你刚讲完一套合同审查方案：固定流水线，模型只做逐条目判定。面试官追问：「现在大家都在做 multi-agent，你为什么不用？什么情况下你会用？」

题面为本书自拟的训练题，不代表任何公司的真实面试题或真实系统。

约束

约束取值（练习设定）
场景 A：合同审查40 个固定清单条目，每份合同逐条判定，结论要可追溯、签字人放行
场景 B：供应商尽调（面试官顺手加的）给一个供应商名字，查工商信息、制裁名单、负面新闻、财报、分包关系；查到分包商时还要继续查分包商
反馈场景 A 有专家标注的评测集；场景 B 只有部分可自动核对的事实（名单命中、注册信息）
预算与时延场景 A 每份 2 个工作日内出意见；场景 B 希望 10 分钟内出初稿
错误代价两个场景都是漏报比误报贵
答到一半再点开：面试官补了一句

尽调上线了一个 multi-agent 版本后，合规官抱怨：同一份报告里，「制裁」和「负面新闻」两个子 Agent 对同一家分包商的结论互相矛盾。

该先问的问题

  1. 步骤能不能事先写成代码？分支是有限、已知的，还是边做边发现的？这决定路径由代码定还是由模型定。
  2. 每一步做得对不对，有没有外部反馈（测试、检查器、工具返回、可核对的事实）？没有反馈的循环只是在猜。
  3. 子任务之间是否独立？能否各自在一个干净的上下文里完成？结果怎么合并，合并错了谁能发现？
  4. 时延和预算哪个更紧？并行省下的是墙钟时间，未必省 token。
  5. 结论要不要可审计、可复现？路径越开放，审计和评测越贵。

一句话框架

代码能定的路径就用代码定；路径事先定不下、又有外部反馈时，才把控制权交给模型；只有子任务真能独立、合并成本可控时，才拆成多个 Agent。

设计取舍表

命名来源：原始工程文章 Building effective agents（2024-12-19）。文中把 workflow 定义为「通过预定义代码路径编排 LLM 与工具」，把 agent 定义为「由 LLM 动态决定自己的过程与工具使用」，并建议只在复杂度能带来可证明的收益时才增加它。注意该文把 orchestrator-workers 也列为 workflow：委派与汇总的骨架可以由代码预设，由一个中心 LLM 动态决定拆出哪些子任务、交给 worker 再汇总。所以要分两个粒度看「谁决定」——顶层骨架和子任务拆解可以由不同的一方决定；而「是否委派给能自主工作的 worker」又是另一个问题。

下表前五行的「什么时候选」概括自该文；「单 Agent 循环」「多个自主 Agent」两行，以及各行的「代价」和「什么证据会让我换」，是本书的扩展。

形态什么时候选代价 / 失败方式什么证据会让我换
Prompt chaining任务能干净地拆成固定的几步，每步之间可以插一道程序检查前一步的错误会一路传下去；步骤多了时延叠加某一步经常需要回头重做，说明步骤不是真的固定
Routing输入有几类明显不同的情况，分开处理效果更好（例如按合同类型走不同清单）分错类就走错整条路；类别边界模糊时误路由集中出现误路由率高，或新类别不断冒出来，改为「路由 + 通用兜底路径」
Parallelization子任务互不依赖，可以分片同时做（逐条目判定）；或同一问题需要多次尝试投票提高把握同一资料被每个分支重复发送时，总 token 会增加；各分支只拿自己那份、上下文更短时，也可能减少，要按输入、输出、缓存读写同口径实测。投票只在错误彼此独立时才有用多次投票的结果高度一致却一起错，说明错误相关，投票没有增益
Evaluator-optimizer有清楚的评价标准，且多改一轮能带来可量化的提升评价标准模糊时会原地打转；评价者与生成者同模型时容易互相迁就第二轮之后的提升接近零，就固定轮数上限或去掉这一环
Orchestrator-workers（代码定委派骨架，模型定子任务）子任务是什么事先定不下，要由模型边看边拆（查到分包商才需要查分包商）；worker 可以是单次调用，也可以是能自主工作的子 Agent拆分和合并都由模型做，出错更难定位；需要设拆分数量和深度上限实际拆出来的子任务总是那几种，就把它们固化成代码路径
单 Agent 循环（本书扩展）路径开放，但每一步都有外部反馈（工具返回、测试结果）路径多，评测和复现更贵；需要步数、预算和停止条件上下文经常溢出，或串行时延超标，且子任务确实独立时，考虑拆分
多个自主 Agent（本书扩展）每个 worker 自己也要循环、决定下一步；子任务独立、各自需要大量上下文，并行能明显缩短时延，合并规则清楚上下文割裂：隐含的判断和放弃过的路径不会传给其他 Agent；合并时的矛盾需要专门处理同预算的公平对照里，单 Agent 的结果不差于它，就退回单 Agent
Two-minute English 口述

两分钟，先结论后展开

口述计时02:00
展开 2 分钟英文口述稿

I start from the simplest thing that can work and only move right on the spectrum when evidence says I should.

If the steps can be written in code, it's a workflow. Contract review is that case: a fixed checklist, so code decides the path, and the model only judges one clause at a time. Running forty clauses in parallel is still a workflow — multiple model calls don't make it multi-agent.

I give the model control of the path only when the steps can't be known in advance and each step gets real feedback, like tool results or tests. Vendor due diligence is closer to that: you don't know you need to check a subcontractor until you find one.

Whether to delegate to workers that act on their own is a separate choice. I'd split work across several agents only when the subtasks are genuinely independent, each needs a lot of its own context, and I know how to merge the results. The main win is wall-clock time. The cost is that agents don't share what they've learned, so contradictions show up at merge time and someone has to resolve them with evidence.

And I'd prove the choice with a fair comparison: same tasks, same budget, same tools and model, repeated runs. If a single agent does as well, I keep the single agent.

Follow-ups 追问

一层一层往下问

  1. 为何不用备选合同审查里 40 个条目并行判定，这不就是 multi-agent 吗？
    先口答，再展开要点
    • 分两条轴看。谁拆子任务：代码事先定好（每个条目一次调用），模型不决定做什么、做几次。是否委派给自主 worker：没有，每次调用是一次独立的模型调用，只做一次指定的判定、不自己决定下一步。所以这是 workflow 里的 parallelization（分片），不是 worker Agent。
    • 调用次数和上下文是否隔离都不能单独当标准。如果子任务由一个中心模型临场拆出来，就是 orchestrator-workers；如果拿到子任务的 worker 自己循环、自己决定怎么完成，才是委派给子 Agent。A02 的「固定大纲内的并行子 Agent」就是代码定子任务、worker 自主完成的组合。
    • 说清这一点的价值：审计、评测和复现都按固定流水线来做，不需要为模型的规划行为另建评测。
  2. 需求变化业务方又要做供应商尽调：查到分包商就要继续查分包商。你的架构怎么变？
    先口答，再展开要点
    • 子任务事先定不下，这一部分适合 orchestrator-workers 或单 Agent 循环；名单比对、注册信息核对这些固定检查仍然用代码做。
    • 先从单 Agent 加工具开始，设步数上限、追查深度上限（例如只追两层分包）和预算。
    • 出现两个信号再考虑拆成多个 Agent：上下文经常溢出，或串行时延超过 10 分钟的目标，而且各个方向（制裁、新闻、财报）确实可以独立查。
  3. 失败反证尽调的 multi-agent 版本里，两个子 Agent 对同一家分包商结论矛盾，编排者选了错的那个。怎么防？
    先口答，再展开要点
    • 根因是上下文割裂：各子 Agent 只看到自己那部分证据，编排者只看到结论摘要。
    • 要求每个子 Agent 的每条结论都附证据（来源、日期、原文片段），编排者按证据合并，而不是按结论投票。
    • 合并前先确认说的是不是同一家公司：制裁名单上的名字和新闻里的拼写可能不同。每条结论带实体 ID 和别名证据（注册号、地址、原文拼写）；对不上的标「身份未确认」，不合并结论，交人核对。
    • 矛盾不静默消解：报告里明确列出冲突和双方证据，交人判断；统计冲突率。冲突率高，说明拆分方式错了，或者这几个方向其实需要共享上下文，应合并回一个 Agent。
  4. 公平对照你说 multi-agent 版本更好，怎么证明？
    先口答，再展开要点
    • 同一个任务集，同样的模型、工具和总 token / 时间预算，每个任务重复跑多次；比较结果质量、成本和结果的波动。
    • 对照组要包括「给单 Agent 同样多的预算」，否则比的是预算而不是架构。
    • 指标要分开看：结果质量、墙钟时间、总 token、合并冲突率。multi-agent 常见的优势是时延，未必是质量。更细的实验设计见 B05。
  5. 评估Evaluator-optimizer 什么时候反而有害？
    先口答，再展开要点
    • 评价标准说不清时：评价者给不出可执行的修改意见，循环只是在换说法。
    • 评价者和生成者用同一个模型、同一套提示时，容易互相迁就，分数上升但质量没变。
    • 做法：设轮数上限；记录每一轮在评测集上的真实提升，提升接近零就停；评价者只看证据和标准，不看生成者的自述。
  6. 运行Routing 把一份外包合同分进了「采购合同」的路径，用错了清单。怎么发现、怎么兜底？
    先口答，再展开要点
    • 路由结果带置信度；低于阈值或落在类别边界上的，走通用路径或转人工确认类别。
    • 路由之后加一道便宜的程序检查，例如合同里出现「外包」「数据处理」等关键条款，但被分到采购路径时报警。
    • 按类别统计误路由率；误路由的代价不对称（外包合同用错清单比反过来更贵），阈值按代价高的一侧设。
Failure Modes 失败模式

这些地方最容易栽

把「多次调用」叫成 multi-agent
  • 症状：架构图上画了一堆 Agent，实际每个都是固定的一次调用；评测和运维按「自主 Agent」去做，成本虚高，真正该测的固定步骤却没人测。
  • 根因：用调用次数、角色名字或上下文是否隔离来判断形态，而不是分开回答两个问题：子任务由谁拆（以及顶层骨架由谁定），以及是否委派给能自主完成子任务的 worker。
  • 防线：画图时给每个节点标两件事：这一层由代码还是模型决定，执行者是单次调用还是自主 worker；上下文共享与否另外标注。评测方式跟着前两件事走。
合并时丢信息，矛盾被静默吞掉
  • 症状：子 Agent 各自的结论都有道理，合并后的报告却自相矛盾，或者只保留了其中一方，另一方的证据消失了。
  • 根因：上下文割裂。子 Agent 之间只通过摘要传递信息，隐含的判断和放弃过的路径都没传过去；合并步骤又按结论而不是按证据处理。
  • 防线：子结论必须附证据和实体 ID；合并规则写成代码或明确的 rubric；同名不同拼写的实体先做别名核对，对不上就标「身份未确认」；冲突显式列出、交人判断；监控冲突率，过高就重新考虑拆分方式。
评价循环原地打转
  • 症状：evaluator-optimizer 每轮都「改进」，评价分数上升，但人工抽查和评测集上的质量不变，token 却成倍增长。
  • 根因：评价标准不清，或评价者与生成者共享同样的盲区。
  • 防线：轮数上限；评价者只看证据和标准；每轮都在评测集上量真实提升，没有提升就停。
Estimate 估算

带着量纲算一遍

问：尽调任务拆成 4 个子 Agent，比单 Agent 省时间吗？省 token 吗？

假设（练习设定，全部待实测）：4 个方向（制裁、新闻、财报、分包），每次模型调用平均 20 秒。单 Agent 串行做完 4 个方向，共 40 次调用，因为前面的发现一直留在上下文里，平均上下文 50k tokens。multi-agent 版本：编排者规划 2 次调用、每次 10k；合并 1 次调用、20k；4 个子 Agent 并行。子 Agent 分两种情况：各自资料互不重叠时，每个 10 次调用、平均上下文 20k；资料大量重叠时（每个都要先读同一批核心资料，还会重复探索），每个 14 次调用、平均上下文 50k。

单 Agent
  输入 token   40 次 × 50k                         = 2.0M
  墙钟时间     40 次 × 20 秒                        = 800 秒 ≈ 13.3 分钟

multi-agent，资料互不重叠
  输入 token   2 × 10k + 4 × 10 × 20k + 1 × 20k    = 0.84M（单 Agent 的 0.42 倍）
  墙钟时间     (2 + 10 + 1) 次 × 20 秒              = 260 秒 ≈ 4.3 分钟

multi-agent，资料大量重叠
  输入 token   2 × 10k + 4 × 14 × 50k + 1 × 20k    = 2.84M（单 Agent 的 1.42 倍）
  墙钟时间     (2 + 14 + 1) 次 × 20 秒              = 340 秒 ≈ 5.7 分钟

（墙钟时间里子 Agent 并行，只计最长的那一支；编排与合并串行。）

结论：在这组假设下，拆分稳定省下的是墙钟时间；token 是省还是费，取决于子任务之间资料重叠多少、上下文增长多快，同一个架构可以是 0.42 倍，也可以是 1.42 倍。这里只算了输入 token，输出、搜索 API 费用和并发排队都没算；也没算质量：合并冲突、上下文割裂带来的漏报，要靠评测集单独量。

敏感性：重叠情况下，如果每个子 Agent 的调用从 14 次降到 10 次，输入 token 变成 2 × 10k + 4 × 10 × 50k + 20k = 2.04M，约等于单 Agent；可见「重复探索」本身就是 token 差异的主要来源之一。

怎么实测：在同一批尽调任务上，分别跑单 Agent 和 multi-agent，记录每次调用的上下文长度、调用次数、墙钟时间、合并冲突数，以及评测集上的漏报率；用实测值替换上面的假设。
